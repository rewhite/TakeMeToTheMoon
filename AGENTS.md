# Project Instructions

- This project is a development and demo prototype for an ongoing hackathon.
- Prioritize fast feature implementation and demos on the actual device. Deployment, production readiness, and store release preparation are out of scope unless the user explicitly requests them.
- Do not require production architecture or an authentication server as prerequisites. Choose the simplest setup needed for development.
- Using development and test API keys directly in the app through local configuration is allowed. Do not commit actual keys to the repository or expose them in responses or logs.
- The target runtime is a standalone Quest 3 app. Prefer an approach that does not require a PC or Python bridge to stay running. Internet access for external AI services is acceptable.
- Split commits by feature or logical fix. Do not bundle unrelated features or changes into one large commit. Keep the files and Unity metadata required for each change together, and write a clear commit message describing that change.
- The 1114 scene uses Meta XR Interaction SDK for grabbing and sockets (`Grabbable`, `SnapInteractor`, `SnapInteractable`); extend these components for related interactions.
- `WebTest/` is a browser test bench for Visko prompting and the Story Director (not shipped). Keep its Scene contract (see `WebTest/README.md`) in sync with what Unity consumes.
- Unity story inventory and progression are owned by `Assets/Scripts/Story/StoryController.cs`. Connect physical selection, UI, Director requests, and video presentation through its public methods/events instead of maintaining separate run state in those integrations.
- `Assets/Scripts/Game/GameManager.cs` owns start/prologue/five-stage/end presentation and skyboxes. SharedVideoPlayer owns the single video player and screen fade; StagePresentation defines per-stage media and reveal timing. Revealing UI does not advance stages; GameStageView holds prefab-local reveal targets. Keep video/narration and the XR rig in the scene, outside disposable screen roots. Prefer assigning preplaced Hierarchy screen roots: reuse them with SetActive and preserve their transforms; only Project prefab assets are spawned/destroyed. StoryController remains optional for presentation-only flow and owns story state when used.
- AI and live video stay in Unity C# (no Python server at runtime): `DirectorClient` answers `StoryController.NextSceneRequested` via OpenAI, and `ViskoStoryBridge` turns `ScenePresented`/`OutcomePresented` into Visko cut/morph prompts shown through `SharedVideoPlayer.ShowExternal`. Keys are set via Tools > Director / Tools > Visko into Git-ignored Resources files.
- Story checkpoints map to GameManager stages: Prologue = broadcast + item grab, Stage 1 dorm, Stage 2 campus (Memorial Church), Stage 3 launch pad (throw items to fuel), Stage 4 low orbit (throw items/people to cut weight), Stage 5 approaching the Moon, Ending = Moon landing.
- `UIInputModeSwitcher` on EventSystem selects mouse UI in Editor/desktop and Meta PointableCanvas input on Android; use its Editor override for Quest Link tests instead of manually toggling input modules before builds.
- The five stages share one persistent scene VideoPlayer and video screen with the prologue. Keep the video panel visible across stage transitions, retaining the previous frame when the next stage has no video; only start/end screen cleanup hides it. Stage prefabs must not duplicate the player; change the shared player's source and playback settings at transitions, with story progression still owned by StoryController.
- Proactively maintain AGENTS.md when the user establishes durable project preferences or when verified project conventions will help future work. Add or update these instructions without asking for separate permission, and briefly report the changes. Keep instructions concise; do not record temporary task details, secrets, or unverified assumptions as permanent rules.
- The 1114 inventory tray uses three independent Meta `SnapInteractable` sockets on Position 1/2/3, each with its own collider, capacity one, and `StoryInventorySlot` pose delegate. `StoryInventoryTray` shares eligibility/occupancy and bob timing; drops must target the specific placeholder, never auto-fill a different slot. Keep `StorySocketSelection` as the adapter to StoryController; scale only the tray visual, and tune item placement using each prop's Tray Snap Anchor.
- Author inventory props, tray, and placement points as preplaced Hierarchy objects visible in Edit Mode. Runtime reveal should only toggle these objects, preserving authored transforms; do not spawn the inventory layout at runtime.
- Inventory selection uses Meta ray grabbing (RayInteractable + ColliderSurface + MoveFromTargetAtAnchorProvider), with direct GrabInteractable/HandGrabInteractable inputs disabled on the five props. Retain their shared Grabbable, SnapInteractor, and audio integration.
- In 1114, keep the item-selection panel, five inventory props, and inventory tray under the preplaced `Item Selection` parent. Prologue video-ended reveal toggles this parent; keep StoryController, shared video, and XR rig outside it.
- Keep the preplaced Wellness Bar outside stage/reveal roots. PalmWellnessDisplay stays hidden on the start screen and allows palm-up display from the prologue onward, gated by GameManager. It uses either Meta hand to show it above an upturned palm (retain the current hand while both are raised) and hides it when turned down or tracking is lost; disable HeadFollowingHUD. WellnessBar reads StoryController state and uses red/orange/green backgrounds for 0–29/30–69/70–100 respectively; do not spawn it at runtime.

- Quest demo remote commands use the shell-permission-protected MoonDebugReceiver and GameManager main-thread dispatch. Reset through StoryController and GameManager, including physical prop homes/sockets; stage1 remote testing deliberately seeds logical test inventory. See Tools/quest-command.sh and the Game README.

- Stage 3 reveals its preplaced FuelThrowGame after the configured visible Visko playback delay. Use Meta ray-grabbable carried props and physical Target.prefab knockdowns on invisible supports (keep the FuelPhysicsTarget roots and fitted box colliders). Keep minigame item home anchors under its Inventory Tray so placement follows tray edits; FuelThrowItem owns idle tilt/spin and assisted throw motion. Thrown minigame props disappear after resolution and cannot be reused in that challenge; cap attempts to available props (up to three). StoryController owns throw counts, wellness scoring and completion; the fuel result replaces the checkpoint 3 Director choice and requests checkpoint 4 only on Continue.

- Fuel Instructions UI colliders (including linked PointableCanvas surfaces outside the canvas tree) must be triggers: keep them raycastable for Meta buttons but non-solid for projectiles. Enforce at reveal and launch; per-pair IgnoreCollision alone is insufficient across collider reactivation.

- Invisible target supports hold target bodies only; FuelThrowItem colliders must ignore them so low throws are not blocked by an invisible shelf near the instruction panel.

- Fuel target supports use the FuelSupport layer (8); projectile Rigidbody/Collider excludeLayers must exclude FuelSupport, preserving target-support collisions even when colliders are re-enabled.

- Mannequin ray selection may hit any body part but always holds the head. Use the shared Meta Grabbable with JointedRagdollRayGrab and per-part RayInteractable surfaces; keep the held head kinematic with smoothed FixedUpdate movement and scale-aware contact/joint tolerances; never move the ragdoll root.

- Stages 1–5 use StageViskoPresentation with the existing StoryController/GameManager. Start directly with the roommate decision; omit the separate dorm opening. Preload the roommate video silently during the prologue without advancing StoryController. Adopt that stream on Stage 1 entry without resending the prompt. Keep the current Visko session playing while the next one prepares; pause unused generation on authored later stages and disconnect on start/end/reset or actual app suspension. Gate presentation on prompt acceptance, chunk boundaries and decoded-frame progress; reveal roommate choices after 2.5 seconds of visible video. After a choice, morph the current stream with outcome_video_prompt and show Continue after Continue Delay Seconds from the click (preserve authored scene timing). Ordinary choices never auto-advance: require Continue plus decoded next-video readiness. The fuel minigame retains its own single Continue. For normal choices, preload the next Director scene on a muted second Visko stream. StoryController gates advancement on both the click delay and decoded standby readiness; atomically swap the screen then retire the previous stream. Retry failures without applying the choice twice. Stage 3 uses its Director launchpad video; reveal the preplaced fuel game after Fuel Reveal Seconds of visible playback. Keep legacy Stage 1 reveal panels disconnected. Stage 2 sends its Director scene/outcome prompts through the same live session with delayed choices and the configured post-choice stage delay. Stage entry requests video even for presentation-only skips, using a location fallback without inventing story state or choices. Keep Stage 3 physical gameplay; suppress Director choice cards and ignore its old local demo clip and do not restore the global StoryFlowConnector/ViskoStoryBridge scene wiring.
- Game Manager Inspector's Prologue-to-Stage-1 preview must start StoryController through the stage1 debug command (with temporary test inventory); ShowStage alone previews video without starting story progression. Advancing from Prologue must preserve the preloaded session instead of resetting the run. Live validation must exercise this same Inspector entry path.

- GameManager crossfades stage panorama images on the skybox itself, preserving the shared video and avoiding full-screen black fades between panorama stages. Keep per-stage rotation/exposure and Quest stereo support; bundle the blend shader via its Resources material.

- Fuel completion uses optional hit-count result prompts (0–3) on FuelThrowGame through StoryController.FuelResultVideoRequested. After final projectile cleanup, send the result prompt once, hide minigame children after Hide Objects After Seconds (default 3), then reveal Continue after Continue After Hide Seconds (default 3 additional seconds). Empty prompts preserve current video. Keep the host and Continue ancestor path active; only Continue completes story progression.

- Continue buttons use the Primary Button prefab. Ordinary stage Continue is a separate preplaced instance under Choice Cards (Story Continue), not a repurposed choice card; retain the existing Meta ray canvas and the fuel game’s Primary Button instance.
